`crates/agent/src/agent_loop.rs:1726-1741`: on a token mismatch the gate logs and **continues the

### Root cause, every step verified by me
1. `tests/partial_approval.rs:347` — the reply channel is `mpsc::channel::<ApprovalReply>(1)`,
   **capacity ONE**.
2. `:357-363` — at turn start the harness spawns a wall-clock timer: `sleep(50ms)` then

3. `:997-1002` — for this test `late` is `ApprovalReply { Deny, token: Some(2) }` — **prompt TWO's

4. `:387` — when a prompt is emitted the harness answers with

dispatched, so the stuck gate is prompt ONE.

`mismatched_reply_while_waiting…` both aim their `late` reply at **prompt one's** token, so

does not exist yet. It is timing-immune by luck of shape, not by design.

**Reproduction:** passes warm (40/40, 0.21 s); **100% hang** under background QoS + 16 CPU

## ⛔ READ FIRST — TWO THINGS THAT MUST NOT AUTO-DEPLOY

A merge-readiness reviewer went through the whole marc27 branch as "what breaks on deploy day". Two
answers matter more than everything else in this file:

**1. `20260807000001_ml_train.sql:42-50` rewrites the `jobs` table under ACCESS EXCLUSIVE.**
`ALTER COLUMN type TYPE TEXT USING type::TEXT` rewrites every row, drops the enum, and adds a
validating CHECK (a second scan) — and `jobs` is the **live job queue**. sqlx wraps the whole file in
one transaction, so the lock is held through `CREATE TABLE training_runs`, its indexes and RLS too.

every `/jobs*` read blocks for the duration, on a routine push, with no operator gate.
**Do not let this ride out on an ordinary deploy.** Either take it in a low-traffic window with
`pg_stat_activity` watched, or land the `jobs` schema change as its own deploy separated from the
other 23 commits so a stall is isolated and diagnosable. The precedent that it can work
(`20260510000055` did the same enum→TEXT on `resources`) does not carry: `resources` is not
write-hot.

`train_gpu_seconds` price by editing `20260807000002` **in place**. sqlx checksums applied migrations
and `Migrator::run` returns `VersionMismatch` when a file stops matching what was applied; main.rs

## NEXT ENGINE INCREMENT — partial approval (design decided, NOT started)

The app's diff view landed (`93482ce`, 100 tests) and honestly reports the limitation it hit:
**per-hunk selection is local staging only.** Verified myself: `ApprovalResponse` is exactly
`{Allow, Deny, AllowAll}` (`crates/agent/src/agent_loop.rs:27-34`), consumed at `:1612-1626` where

agent's FULL proposal no matter what the user deselected.

**Design decision, so whoever picks this up does not get it wrong: the client sends a SELECTION
MASK, never modified text.**

- Engine computes the hunks from `(old_text, proposed_new_text)` and includes them in the pending
  approval event; the client selects by index; the engine applies the selection itself.
- The alternative — client posts a rewritten `new_text` and the engine validates it — means the
  engine must prove an arbitrary string is a legitimate subset-application. That is a
  verification burden with a widening risk attached, for no benefit.
- With a mask, a buggy or hostile client can at worst apply a SUBSET of what was already
  presented. It cannot inject content the agent never proposed. That property is why this shape.
- Both sides must agree on hunk indices, so the hunking must live in a PRISM crate the app
  consumes — not be reimplemented in `prism-app/src/diff.rs`.

Touches the approval gate, which is the surface round 7 spent five rounds hardening. Needs its own
careful pass plus ≥2 adversarial reviews; not something to bolt on at the end of a session.
