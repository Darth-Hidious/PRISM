### CRITICAL correction to the mission premise (honesty)

The mission states *"most input schemas are empty (`{"type":"object"}` with no properties/descriptions/examples)"*. **This is outdated for the Python side.** Verified count:
- **Python (67 tool defs): only 6 have empty schemas** (`agent_capabilities`, `check_hpc_queue`, `list_background_research`, `list_models`, `show_scratchpad`, `spark_status`) — and all 6 are *genuinely parameter-less* read/list ops. 61 have rich schemas with per-property descriptions, enums, `required`, `additionalProperties`.
- **The real schema gap is the Rust command-tools.** 77 `CommandToolSpec`s; ~7 kinds use `empty_schema()` and many `RootArgs`-kind tools expose only a generic `args: array<string>` (`root_args_schema` `command_tools.rs:822`) — **zero type information** for the model. This is where "empty schema" is actually true and harmful.

The AUDIT (Phase 2) will correct the premise with a measured table and redirect Phase 4 tool-upgrade effort to the Rust command-tools (where the gap is real), not the Python side (which is mostly healthy). I will not pad the Python upgrade work to match a premise the data doesn't support.

### PHASE 2 — Audit (`docs/TOOL_SURFACE_AUDIT.md`)

A measured, per-tool table + structural gaps. Built by running the live registry (reuse `scripts/gen_tool_catalog.py`'s `build_full_registry()` approach) **and** iterating the Rust `COMMAND_TOOLS` static array.

**Per-tool table columns:** name | source (Python/Rust-command) | description-quality (✅/⚠️/❌ + one-line reason) | schema-completeness (typed-props count, empty?, has `required`? per-prop descriptions? examples?) | output/result contract (data vs handle, size cliff) | context needs | permission/approval | provenance.

**Structural gaps section** (the real findings):
- Rust command-tools: the `args: array<string>` / `empty_schema()` gap (the actual "empty schema" problem).
- Description thinness where it exists (a minority).
- `agent_loop.rs` context flow audit: how turn-to-turn state moves (history + SESSION MEMORY + scratchpad-not-surfaced + result_store turn-local + provenance cross-turn). Verdict: **chat-turn-shaped**; no `Task`/plan object in the loop; no loop-level resume; scratchpad is an audit log, not model-facing working memory.
- Three-sources-of-truth drift risk (Python defs / Rust specs / permissions map).
- Output contracts: command-tool results are inlined JSON (truncated 30 KB) — the model gets blobs, not typed handles, at the tool boundary.

### PHASE 3 — Spec (`docs/TOOL_SURFACE_SPEC.md`)

The standard the surface must meet + a **definition-of-ready** gate. Defines:

1. **Schema convention** — rich JSON Schema (typed params, per-param `description`, `examples`, `enum`/`minimum`/`maximum` constraints, `required`, `additionalProperties:false`). A parameter-less tool MUST declare `{"type":"object","properties":{},"additionalProperties":false}` explicitly and its description must state it takes no arguments. The generic `args: array<string>` escape is **forbidden** for any tool that actually has distinct arguments.
2. **Description-writing standard** — each tool description must contain: **purpose** (what it does), **when-to-use** (and when NOT), **side effects / cost / latency**, **returns** (shape + whether a handle/blob). Minimum length floor + must reference at least one "when to use" signal.
3. **Context-passing contract** — what every tool receives (task goal, plan position, prior artifacts by reference), how results flow back (typed result objects; large results referenced by provenance handle, never inlined > N chars), how node-fetched data is referenced (handles into the provenance store, fetched via `recall`/`fetch_artifact`), how long-running state persists/resumes (checkpoint spine).
4. **Retrieval maturity** — extend `capability.rs`: embed example queries alongside `"{name}: {description}"` (Tool2Vec), document the progressive-disclosure tiers already shipped, spec the rerank step.
5. **Definition-of-ready** — the checklist a tool must satisfy to be admitted (non-empty typed schema passing the lint, description meeting the standard, permission mapped, output contract documented, provenance-recorded). The CI lint (Phase 4) enforces this mechanically.

### PHASE 4 — Implementation (test-first, don't break v1)

**4a. CI lint — schema + description quality (both sides)**
- **Python:** `scripts/lint_tool_schemas.py` — imports `build_full_registry()`, iterates every `Tool`, asserts: description meets length/signal floor; `input_schema` is a real JSON object; if it declares properties, each has a `description`; parameter-less tools must set `additionalProperties:false`. Fails CI with a per-tool report. Add as a step in `.github/workflows/integration-test.yml` python-tools job.
- **Rust:** a new `#[test]` in `crates/agent/src/command_tools.rs` (or `tests/`) iterating `COMMAND_TOOLS`: asserts each spec's `schema_for_spec` is not `empty_schema()`/`root_args_schema()` unless the tool is genuinely parameter-less (an explicit allowlist), and that descriptions meet a floor. Plus a `#[test]` that every `COMMAND_TOOLS` name has an entry in `tool_permissions()` (catches the drift where a new command-tool silently defaults to `WorkspaceWrite`).
- **Rust consumption gate:** harden `ToolCatalog::from_tool_server_json` (`tool_catalog.rs:52`) — when `input_schema` is absent, log a warning with the tool name (today it silently defaults); keep loading so v1 doesn't break, but surface the gap.

**4b. Upgrade tools to spec, batch by batch**
- **Batch 1 — Rust command-tools (the real gap):** replace `root_args_schema`/`empty_schema` for the tools that have real distinct arguments. For each, write a typed JSON Schema with per-param descriptions matching the actual CLI args. Genuinely parameter-less tools (e.g. `workflow_list`, `node_status`) get the explicit `additionalProperties:false` empty form + a description stating "takes no arguments." Bring descriptions up to the standard (purpose/when-to-use/returns).
- **Batch 2 — Python thin spots:** the few empty-schema Python tools that should stay parameter-less get `additionalProperties:false` + description touch-ups; any description that lacks a when-to-use signal gets one. (Small batch — the Python side is mostly healthy.)
- **Batch 3 — descriptions across both sides** where the audit flagged thinness (when-to-use/when-not/returns).
- After each batch: `cargo fmt && cargo clippy --workspace --all-targets -- -D warnings && cargo test --workspace` for Rust; `PRISM_DISABLE_MEMORY=1 python3 scripts/lint_tool_schemas.py` for Python; regenerate `docs/TOOL_CATALOG.md`.

**4c. Context-passing / long-running-task plumbing — the BRIDGE** (the chosen architecture: *Task over campaign checkpoint driving run_turn turns*)

Goal: one durable spine (the campaign checkpoint contract) driving one tool-dispatch path (`run_turn`), honoring the owner's "retire redundancy" decision and the mission's "in agent_loop."

Concrete steps (each a small, tested commit):
1. **Generalize the campaign iteration body.** Today `run_iteration` (`campaign/src/lib.rs:427`) is hardcoded propose/evaluate/rank and builds its own LLM client. Introduce an iteration-body trait/enum so a campaign can be either `Materials` (today's body, unchanged) or `Research` (delegates to `run_turn`). Add `CampaignGoal` fields for a generic research goal (natural-language objective, constraints, success-criteria) without breaking the materials shape. Keep `Candidate`/reward for the materials branch; the research branch stores plan steps + artifact handles instead.
2. **`ResearchTask` context object in `agent_loop`.** Add an optional `task: Option<&ResearchTaskContext>` parameter to `run_turn` (defaults to `None` → chat behaves exactly as today; **chat is not broken**). When present, the turn: (a) injects the task goal + plan position + prior artifact handles into the system prompt block, (b) treats the turn as one step of the task, (c) on completion, updates the task's plan position and writes any new artifact handles. `user_message` when task-driven is synthesized from the next plan step (or "continue the research task").
3. **Artifact handles, not inlined blobs.** Formalize the existing `process_large_result`/`result_store`/`recall` pattern into the context-passing contract: node-fetched data and any result > N chars gets a typed handle into the provenance store; the model sees `{ "artifact_ref": "prov:<id>", "summary": "..." }` and pulls full content via `recall`/`fetch_artifact`. This makes the cross-step/cross-turn data flow reference-based for long tasks.
4. **Resume.** The research campaign checkpoint (`~/.prism/campaigns/{id}.json`) holds goal + plan position + artifact refs + budget/iteration + approval-gate state. On resume, `run_turn` is re-driven from the checkpointed plan position with the checkpointed artifact handles in context. Reuses the existing `--detach` worker + poll-via-checkpoint contract (already in `crates/cli`).
5. **Scratchpad becomes model-facing working memory for task-driven turns** (opt-in when a task is present): surface the task's running notes (hypotheses, dead-ends, next steps) in a system block, so the model carries intent across the 20-iteration inner cap. Chat turns remain unaffected.

Each step: tests on the touched crate (`crates/agent`, `crates/campaign`). The chat path stays green at every commit (verified by existing tests + a new test asserting `run_turn` with `task=None` is byte-for-byte the prior behavior). No network/LLM in tests — use the deterministic fake paths and unit-test the context-block construction / checkpoint serialization.

### Risks (and mitigations)
- **Breaking chat / the v1 binary.** Mitigation: `run_turn` task param defaults to `None`; a test asserts the chat path is unchanged; `prism` (no-args chat) entry is untouched. The generalized campaign keeps the materials branch byte-identical.
- **The `tool_permissions()` 94-entry test** (`permissions.rs:418`) breaks when new tools appear. Mitigation: Batch 1 only changes schemas/descriptions of *existing* specs, not names; the new drift-catch test makes future drift loud, not silent.
- **Over-reaching the mission on the bridge** (generalizing campaign is scope beyond "agent_loop.rs"). Mitigation: this is the explicitly chosen architecture; it's the only way to have *one* durable spine + *one* tool-dispatch path, matching the owner's "retire redundancy" decision. The materials path is preserved.
- **Research quality** — the mission demands real citations. Mitigation: every Phase-1 finding cites a primary source; inferred recommendations are labeled as such.
- **Lint false-positives** on genuinely parameter-less tools. Mitigation: the lint allows `additionalProperties:false` empty objects with an explicit "no arguments" description; an allowlist exists for truly arg-less tools.
