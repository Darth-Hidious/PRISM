### Commit G1 — jupyter/ipykernel ANSI traceback leak (HIGH, the preferred backend)

**Defect:** `filter_notebook_traceback` is a verbatim NO-OP on ipykernel traces. ipykernel wraps `File` in ANSI (`\x1b[96mFile\x1b[39m`) so `starts_with("File ")` never matches; frames read `File ~/path:N, in func` (unquoted, `~`-collapsed, colon separator) or `Cell In[N], line M` — not stdlib's `  File "...", line N`. Result: 0 frames matched → elided=0 → raw ANSI site-packages frames leak to the model. Only the Rust notebook filter is affected (the Python twin handles only execute_python's stdlib subprocess traces).

**Fix (`crates/agent/src/command_tools.rs::filter_notebook_traceback`):**
1. **Strip ANSI first.** A `strip_ansi(s) -> String` helper using the regex `\x1b\[[0-9;]*m` (covers every SGR code ipykernel emits — verified: `\x1b[91m`, `\x1b[96m`, `\x1b[38;5;15m`, etc., all end in `m`). Apply at the top of the filter, before line-splitting/matching. Keep the ORIGINAL (ANSI-stripped) text as what flows to the model (ANSI codes in tool output are noise to the model anyway).
2. **Recognize IPython frame forms.** A frame line matches if (after ANSI strip + trim) it starts with `File ` OR `Cell In[`. The existing `is_library` path-substring check (`site-packages` etc.) stays valid once ANSI is stripped (numpy frames carry full site-packages paths). The continuation-line logic (`    `-indented source/caret) already works post-strip.
3. Keep the final exception line logic (it already keys on the non-`File`/non-indented line — works for both `\x1b[91mIndexError\x1b[39m: msg` post-strip and stdlib `EType: msg`).

**Tests (the exact gap):** use the REAL captured ipykernel ANSI `repr()` fixture (from the verification agent): `\x1b[91m---...\x1b[39m\x1b[91mIndexError\x1b[39m ... \x1b[96mFile \x1b[39m\x1b[32m~/path:N\x1b[39m, in \x1b[36mfunc\x1b[39m\x1b[94m()\x1b[39m\n... \x1b[91mIndexError\x1b[39m: msg`. Assert: ANSI stripped, library frames collapsed, final line kept, `traceback_elided_frames > 0`. A hand-written stdlib trace does NOT prove this path.

### Commit G2 — subagent chain snapshot/restore (MED)

**Defect:** `reset_code_run_chain()` runs at `run_turn` entry; `spawn_subagent` re-enters `run_turn` NESTED on the same process-global `LAST_CODE_RUN`. (a) The subagent's entry-reset WIPES the parent's in-flight chain (parent loses its parent_id). (b) The subagent's leftover record is never cleared on return → parent's next code call chains against the subagent's record.

**Fix (`crates/agent/src/hooks.rs` + `crates/agent/src/subagent.rs`):**
- Add `pub fn snapshot_code_run_chain() -> HashMap<String, LastCodeRun>` and `pub fn restore_code_run_chain(map)` in hooks.rs (clone the map / replace it).
- In `subagent.rs::execute_spawn_subagent_inner`, snapshot BEFORE `nested.await` and restore AFTER (parent's chain survives intact; subagent's is isolated + discarded). Mirror the existing `before_ids` snapshot pattern at subagent.rs:273-276.

**Tests:** parent python fails → spawn_subagent (its python also fails) → parent retry gets the PARENT's parent_id (not the subagent's); the parent's pre-subagent chain is intact. Test the snapshot/restore helpers directly (pure fns).

### Commit G3 — library over-elision (LOW)

**Defect:** `is_library`/`_is_library_frame` do unconditional substring matching; `python3.`/`/lib/python`/`/Frameworks/` are ambiguous — a user path like `<cwd>/scripts/port_python3.14_helpers.py` is wrongly elided.

**Fix (both `command_tools.rs::is_library` and `code.py::_is_library_frame`):** split the markers:
- **Reliable** (`site-packages`, `dist-packages`): unconditional library (a venv under cwd is still library — keep the F2 fix).
- **Ambiguous** (`python3.`, `/lib/python`, `/Frameworks/`): library ONLY if the frame path is NOT under cwd. Re-introduce a cwd check for these (the Rust `cwd` param becomes load-bearing; the Python twin already takes cwd).

**Tests:** `<cwd>/scripts/port_python3.14_helpers.py` → user frame KEPT; `<cwd>/.venv/lib/python3.14/site-packages/numpy/…` → library ELIDED (the site-packages marker still wins).

### Commit G4 — chained-exception per-block collapse (LOW)

**Defect:** once a chain marker (`During handling…` / `The above exception…`) is hit, everything after is kept verbatim → raw library frames in the second block leak.

**Fix (both filters):** apply the library-frame collapse to EACH block of a chained exception, not just keep the tail whole. Reframe: a chain marker RESETS the frame-walk (flush any pending library run, then continue the normal File/library/final-line classification into the next block). Keep BOTH final exception lines; collapse library frames in BOTH blocks. The `hit_chain` short-circuit is removed in favor of continuing the walk.

**Tests:** a chained numpy failure (both blocks with library frames) → library frames collapsed in both blocks, both final lines kept.
